# 逃生路径（v0.4）

> 这一份回答一个问题：**当派出所拦住了你，你还能做什么？**
>
> 一份"什么都不能做"的治理不是治理，是瘫痪。用户真正需要的不是"插件说不行"，
> 而是"插件说不行，并且告诉我可行的那条路"。
>
> 配套测试：`tests/unit/v04-refusal-text.test.js`（文案里点名的每个工具都必须真实注册）。

## 硬规则

> **拒绝文案里出现的每个工具名、每条替代路径，都必须在当前插件里真实存在且可用。**

这不是措辞问题。v0.3 的根文案说「岗位模型策略只在 `dispatch_agent` 上生效」，
而这句话对 `send_message` 是**错的**——它根本不涉及路由。用户照着这句话去改
一个跟问题无关的东西，比不给提示更糟。

`tests/unit/v04-refusal-text.test.js` 的 T70 会从真实拒绝文案里抓出所有
`` `名字` `` 形式，逐个核对它们确实注册着。

## 按场景列出

### 1. 受管根会话想派一个子智能体

| 想做的事 | 唯一正确路径 | 为什么别的路被拦 |
| --- | --- | --- |
| 派一个新的子智能体 | `dispatch_agent`（带 `roleId`） | 原生 `subagent` 等入口会绕过岗位模型策略：它能指定任意模型，而 `dispatch_agent` 会把路由钉在台账上 |
| 看有哪些岗位可选 | `dispatch_roles` | — |
| 想试试某个岗位能不能派 | `station_status` 带 `roleId`（dry-run，不会真的派出） | — |

**如果你确实需要原生入口**：让用户把 `blockNativeDelegation` 设为 `false`。
那时插件退化成"只记录、不拦原生入口"——这是一个明确的选择，不是 bug。

### 2. 受管根会话想给已派出的子会话追加指令

用 `send_message`，**在受管根会话里用**。

`send_message` 不创建 agent（`createsAgent: false`），所以它不涉及"绕过岗位模型策略"。
v0.4 的目录把它写成 `rootVerdict: 'allow'` —— 受管根里随便用。

> v0.3 在这里是错的：`decideToolPolicy` 把 `deny-in-child` 与 `deny-managed` 合流，
> 于是 `send_message` 在受管根上也返回 `deny: true`。用户报的"排出去的智能体
> 没法追加上下文"就是这个。

唯一会被拦的情况：目标不属于本根（`TARGET_FOREIGN`）或无法解析（`TARGET_UNKNOWN`）。
那时按提示核对 `agent_id`。

### 3. 受管子会话想再派孙级

**没有直接路径**——这是设计如此（`forbidNestedDispatch` 默认 `true`）。

可行的替代：

| 做法 | 怎么做 |
| --- | --- |
| 把工作带回主会话 | 在自己的最终回答里说明"需要再派一层，请主会话处理" |
| 给主会话发消息 | `send_message` 给直接父会话（`childVerdict: 'allow-if-parent-or-known'` 明确允许） |
| 让用户显式放开 | 用户设 `forbidNestedDispatch: false`。那时孙级会被允许，但受管根的深度上限仍由宿主的 `maxDepth` 决定 |

**子会话给直接父发消息是被明确允许的**，这不是宽松，是必要：子会话能做的
只是"提供信息让父继续工作"，那本来就是子智能体的正常用途。真正的风险是
"子会话让父去派生新子智能体"，而那条路径被 L2 拦住（父会话的 `dispatch_agent`
仍受岗位约束）。

### 4. 你想让某个会话受管

两种方式（`station_status` 在未受管时会同时给出这两个）：

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| 精确 | 把会话 id 加进 `managedSessionIds` | 只治理特定几个会话 |
| 自动 | 把 `manageAllNewRoots` 设为 `true` | 所有**新的根**会话自动受管（已有的不受影响） |

**生效时机**：写入后的**下一个工具调用**立刻生效（零窗口）。不需要重启、不需要重载插件。
这是 v0.4 修掉问题 1 的核心——判定不在挂载时刻定稿。

### 5. 某个工具被误拦（它在目录外，但名字像派生入口）

两条路，取决于真相：

| 真相 | 做法 | 结果 |
| --- | --- | --- |
| 它确实能派生子智能体 | 把名字加进 `blockedToolNames` | 它会在受管会话里被持续拦截（明确的决定，而不是"因为我们不认识它"） |
| 它是无辜的普通工具 | 升级插件目录（或把 `unknownEntryPolicy` 改成 `allow`） | 它不再被误拦 |

`station_status` 的覆盖诊断会把这些名字列出来（`unknown-present` 档），
所以你不需要自己去猜哪些工具在目录外。

### 6. 台账坏了

**没有逃生路径，这是刻意的。** 台账打不开时插件拒绝所有派出（`LEDGER_UNAVAILABLE`）。

理由：没有台账就无法回答"这个子会话为什么被允许、该用哪个模型"。
放行等于把一个安全承诺变成装饰。

修复路径：检查存储服务 → 重启插件 → `station_status` 看 `台账：正常`。
数据不会丢（卸载不删台账），但**未完结的回执会被标成 `unverified`**，且不会自动重派。

### 7. 谱系被改写过（resume / clear / 换父）

`LINEAGE_MISMATCH` / `LINEAGE_UNKNOWN` 时，插件拒绝该子会话的请求。

**没有自动修复路径**，因为正确的做法取决于"到底该算哪个根"——那是人的判断。
处置顺序：

1. `station_status` 看该子会话的 `谱系根` 与台账记录；
2. 决定哪个是对的；
3. 如果台账记录错了，删掉那条 children 登记（或清空该根的台账重建）；
4. 如果谱系真的被改了（比如 resume 到别的父下），重建登记。

### 8. 想完全关掉治理

三档，粒度从细到粗：

| 想要 | 配置 | 影响 |
| --- | --- | --- |
| 只关原生入口拦截 | `blockNativeDelegation: false` | `dispatch_agent` 仍受岗位约束，原生入口放行 |
| 关受管模式 | `requireManagedSession: false` | 任何会话都能派出（但仍受岗位/路由约束） |
| 完全停用 | 卸载插件 | guard 与锁定随 effect 一起撤销，台账保留 |

第三档之后原生入口恢复可用、请求不再被压回——`tests/unit/v04-timing.test.js` 的 T69
双向验证这一点（卸载后既不能继续拦，也不能丢失台账）。
